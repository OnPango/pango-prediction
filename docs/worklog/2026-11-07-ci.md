# CI: quality gates and a Docker smoke test on every PR

**Date:** 2026-11-07 · **Branch:** `feature/ci` → `dev`

## Goal

Run the quality gates and check the CPU image automatically on every PR into `dev` or `main` and on every push to them. The owner reviews from a phone, so each PR has to show by itself whether it is green.

The two jobs:

- **`checks`:** Python 3.12, the `pip` install from `AGENTS.md`, then pytest, ruff and mypy. Lint and types still run when the tests fail.
- **`docker`:** builds `docker/Dockerfile.api`, then smoke-tests the image:
  - it exits without a service credential;
  - with one, it answers `/health`;
  - `/v1/forecasts` answers 401 without a token;
  - with the token, a fixture request gets 200.

**Local Docker build — an environment workaround, not a repository change.** The session's network blocked a build of the unmodified Dockerfile in two ways:

1. Docker Hub rate-limited the pull of `python:3.12-slim` (429). The same image was pulled from `mirror.gcr.io` instead.
2. `pip` inside the build did not trust the session proxy's CA. The local build used a copy of the Dockerfile with two lines added after `FROM`: one copies the proxy CA, one sets `PIP_CERT`.

The repository's Dockerfile is unchanged. GitHub's runners build it as it is, and the PR's CI run is the check of that.

## Decisions

- **The install is the same `python -c` line as `AGENTS.md`**, so CI, the owner's machine and the cloud session install the same way from `pyproject.toml`.
- **The smoke test checks behaviour, not only the build.** "Refuses to start without a credential" and "401 without a token" are security properties of the image. A unit test covers the factory, but only a container run covers the image as deployed.
- **Nothing is published or deployed.** Permissions are read-only. Pushing an image needs a registry and a deployment target, which have not been chosen.
- **Triggers include `main`**, so a future release PR from `dev` into `main` is checked too.
- **Lint and types run after a test failure.** One run then reports every problem, which matters when reading CI from a phone.

## Open questions

- **Whether GitHub Actions is enabled for the `OnPango` organization.** The PR's CI run will show it.
- **Branch protection on `dev`.** Requiring CI to pass before a merge is a repository setting only an admin can turn on.
- **Lock file.** It remains a separate decision. Without one, CI resolves the newest versions that satisfy `pyproject.toml`, so a run can break when a dependency releases.
